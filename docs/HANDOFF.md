## 화면 녹화 (2026-09-18)

IBM BoB Level 3 제출 영상용 **디스플레이 수동 녹화**를 "화면 녹화" 메뉴로 만들었다.
구조는 [ARCHITECTURE](ARCHITECTURE.md#화면-녹화), 규격·측정은
[VIDEO-QUALITY](VIDEO-QUALITY.md#화면-녹화), 결정 근거는
[SCREEN-CAPTURE-DESIGN](SCREEN-CAPTURE-DESIGN.md)에 있다.

확인한 것: 실제 DELL 10초 녹화를 앱과 같은 작업자·신호로 정지해 영상·음성 10.600초,
dup/drop 0. 취소 시 파일이 남지 않음. 실제 Electron 창에서 화면 목록 → 녹화 → 정지 →
완료 화면까지 동작. 녹화 → 기존 목소리 후보로 구간 교체 → 덱 1080p와 합치기가 복사로
끝남. `doctor`의 화면 기록 판정. `npm run check` 통과(앱 333·Python 298).

확인하지 않은 것: 실제 Bob 조작 15분 녹화와 그 영상의 시청 확인, 새 목소리 만들기부터
이어지는 전 과정(구간 교체에는 9월 17일 목소리 후보를 썼다), 1440p 모니터 녹화.
구간 음성 교체는 한 번에 120초까지라 긴 녹화의 내레이션은 여러 번 나눠 넣는다.
나눌 때마다 영상은 복사되지만 음성 트랙은 AAC로 다시 압축된다.

**결정 필요:** 음성 포함 녹화는 이 Mac에서 쓸 수 없다. ffmpeg가 마이크 소리의 약 13%를
놓쳐 검증에서 걸리고, 그 녹화에 내레이션을 넣으면 최대 0.7초 밀린다. 토글은 설계대로
두되 켜면 경고를 보이고 결과는 검증 실패로 남는다. 고치려면 설계에서 뺀 네이티브 녹음
또는 앱 창의 브라우저 녹음 API가 필요하다. 기본인 무음 녹화에는 영향이 없다.

## 앱 데모 촬영 (2026-09-20)

직접 만든 앱을 자동으로 조작하며 찍어 소개 영상을 만드는 경로를 만들었다. CLI로만 돌고
앱 화면 메뉴는 아직 없다. 실행법은 [README](../README.md#앱-데모-촬영-cli), 구조는
[ARCHITECTURE](ARCHITECTURE.md#앱-데모-촬영), 규격·측정은
[VIDEO-QUALITY](VIDEO-QUALITY.md#앱-데모-촬영), 결정 근거는
[APP-DEMO-DESIGN](APP-DEMO-DESIGN.md)에 있다.

확인한 것: 우리 Electron 44 + playwright 1.62 `_electron`으로 픽스처 앱을 띄워 타이핑 →
승인 대기 → 클릭 → 완료 대기를 실제로 찍고(장면 시각·좌표·화면 글, 무손실 gbrp 원본,
`finish({ endAt })`가 상한이 아닌 실제 끝 시각에서 끊음), 그 촬영을 렌더해 프레임 수 =
계획 길이·음성이 계획한 자리·자막·검증 보고서까지 확인했다. 커서와 클릭 지점 확대가
완성 영상에 실제로 찍혔다(`output/reviews/2026-09-20/app-demo-build/fixture/`).
`demo voice`는 실제 제작 목소리(Qwen3-TTS + `jaeho-ko-r16-v1` 0.60)로 한 후보를 만들어
그 음성으로 렌더까지 돌렸다. `zoompan`의 정수 좌표 떨림은 4K 입력에서 실제 값을 역산해
쟀고 설계 움직임에서는 묻힌다고 판단했다. `npm run check` 통과(앱 366·Python 298).

RICE 파일럿을 두 번 돌렸다. 시나리오를 고치지 않고 `config/demo/rice-core-flow.json`
그대로 기동·타이핑·승인 대기·클릭·완료까지 갔고, Ollama가 실제로 파일을 만들었다.
첫 촬영에서 **커서가 엉뚱한 자리에 찍히는 결함**을 찾아 고쳤다(창 위의 실제 마우스가
오버레이를 끌고 갔다. 지금은 우리가 보낸 좌표로 그리고 창은 `setIgnoreMouseEvents`로
둔다). 회귀 검사를 넣었고 두 번째 촬영에서 제자리를 확인했다.

결과는 `output/edits/2026-09-20/rice-core-flow/`다. 55.0초 촬영 → **21.9초 완성본**이며
1440p·4K 두 벌이다. 대본·목소리까지 전 과정을 한 번 돌렸다: 장면 3개에 후보 3벌씩
실제 제작 목소리로 만들고, 1번 후보로 렌더해 프레임 수 = 계획 길이·음성 길이 = 영상
길이를 확인했다. 내레이션이 계획한 자리(0.3s·4.5s·16.7s)에서 실제로 들리는지 음량으로
확인했고 자막도 나왔다. 결과 폴더의 `review.html`이 영상·구간·확대·대본·후보 음성을
한 쪽에 모은다.

첫 완성본에서 사용자가 **RICE가 "알아이씨이"로 읽힌다**고 지적해 고쳤다. inline 항목은
영어 음성으로 가지 않고 한국어 모델이 철자를 직접 읽는데, 대문자 약어라 철자로 읽혔다.
철자를 재서(`probe_term_pronunciation.py`) 자막 원문은 `RICE`, 발음문은 `Rice`로 나눴고
다시 만든 후보 3벌이 모두 `라이스`로 읽혔다(거리 0.000). 자막이 어디 있냐는 지적으로
검수 화면에 자막을 덱과 같은 모양으로 겹쳐 그린다 — 영상에 굽지는 않는다.

`ask` 장면에는 영어 목소리로 읽은 표본 둘을 후보로 함께 넣어 두었다(제작 경로가 아닌
청취 실험이다). 고르면 `speech_segments` 규칙을 바꿔야 한다.

2026-09-21 사용자가 그 영상을 보고 들었다. 시청·청취에 지적이 없어 1440p 기본·빨리
감기 4배·확대 1.6배·자막 파일 기본이 확정됐고, `ask` 장면의 영어 목소리 표본은 미채택,
RICE 저장소 수정은 승인됐다. 확정 내용은
[APP-DEMO-DESIGN](APP-DEMO-DESIGN.md#6-파일럿-영상으로-닫은-결정-2026-09-21)에 있다.

같은 날 이 작업에서 물린 기록 결함 둘을 고쳤다. `probe_term_pronunciation.py`는 철자만으로
클립 이름을 지어 macOS에서 `RICE`와 `Rice`가 한 파일이 됐다(보고서 수치는 무사하지만
남는 음성은 마지막 철자 것뿐이었다). 이제 순번이 이름의 신원을 맡는다. 후보 기록의
`voiceRouting`은 영어 구간이 있을 때만 적혀서 "영어가 없었다"와 "적지 않았다"가 같아
보였다. 이제 없을 때도 `null`로 적고 앱의 후보 목록(`index.json`)과 데모 검수 화면이
그 사실을 함께 보인다. `npm run check` 통과(앱 372·Python 302).

확인하지 않은 것: 자막을 영상에 굽는 길은 아직 없다 — 이 맥 ffmpeg에 libass·drawtext가
없고 overlay만 있어(2026-09-21 확인) 브라우저로 자막 그림을 만들어 겹치는 경로가
필요하다. 기본은 끄고 필요할 때 켜는 선택지로 만든다.

승인에 따라 RICE를 고쳤다. `RICE_DEMO=1`일 때만 켜지고 꺼져 있으면 예전과 같다. 무엇이
달라지는지는 rice 저장소의 `demo/README.md`가, 왜 그렇게 정했는지는
[APP-DEMO-DESIGN](APP-DEMO-DESIGN.md#7-rice-데모-모드-승인-2026-09-21-구현-같은-날)이 소유한다.
시나리오도 `bob/rice/demo/scenarios/rice-core-flow.json`으로 옮겼고 이 저장소의
`config/demo/`는 없앴다. 촬영 명령의 시나리오 경로가 바뀐다.

확인한 것: 실제로 띄워 쟀다. 빌드된 화면(`file://`)으로 뜨고 DevTools는 열리지 않으며
`<html data-demo="0.25">`가 붙는다. 시간 배율은 장면 시계가 벽시계 2초에 0.5초 흐르고
(배율 1에서는 2.0초), CSS 재생 속도가 0.25, 온보딩 단계 전환이 4.8초 → 20.4초로 늘었다.
옮긴 시나리오로 실제 촬영까지 돌려 4K 69.0초·1726프레임(복제 173)을 받았고, 그 프레임에
개발 도구가 없고 "저장 위치" 줄이 겹치지 않는 것을 눈으로 확인했다. `npm run check`
통과(앱 372·Python 302). 측정 기록은 `output/reviews/2026-09-21/rice-demo-mode/`,
촬영 결과는 `output/edits/2026-09-21/rice-demo-mode-check/`다.

확인하지 않은 것: **3D 시네마틱을 실제로 찍어 4배로 감은 완성본은 아직 없다.** 이번
시나리오에는 그 장면이 없다 — 온보딩을 여는 장면을 넣어 다시 찍어야 그림으로 확인된다.
패키징(`electron-builder`)한 앱에서의 데모 모드와 1440p 촬영도 돌리지 않았다.
시간 배율은 온보딩 장면에만 건다. 네트워크가 정하는 시간(AI 응답)은 늦추지 않는다.

## 3D 시네마틱 촬영 (2026-09-21)

RICE 첫 실행을 데모 모드로 찍어 **3D 시네마틱이 4K에서 부드럽게 나오는 것을 확인했다.**
시나리오는 `bob/rice/demo/scenarios/rice-first-run.json`(언어 선택 → 각성 → 루프 → 능력
→ 모델 연결 → 투어 건너뛰기 → 채팅)이고 결과는
`output/edits/2026-09-21/rice-first-run/`이다. 92.2초 촬영 → **26.7초 완성본**, 1440p와 4K
두 벌이다. 측정은 `output/reviews/2026-09-21/rice-first-run/measurements.json`,
수치의 뜻은 [VIDEO-QUALITY](VIDEO-QUALITY.md#느리게-찍어-되돌리기-2026-09-21-첫-실행-촬영)에 있다.

이 촬영으로 엔진에 두 가지가 생겼다. 시나리오의 장면이 `timeScale`을 적으면 편집이 그
장면을 통째로 되돌린다(기다림만 감으면 같은 장면이 두 속도로 흐른다). 완성본은 화질마다
다른 이름으로 나가 1440p와 4K가 한 폴더에 함께 남는다 — 예전에는 뒤에 낸 화질이 앞의
것을 덮어써서 검수 화면의 해상도 비교를 쓸 수 없었다.

찍으면서 걸린 것 둘. 온보딩이 끝나면 **화면 투어**가 뜨고 그 배경이 클릭을 삼켜, 첫
시도는 입력칸이 focus를 받지 못해 승인 단추를 180초 기다리다 실패했다(시나리오에 투어
건너뛰기 장면을 넣었다). 온보딩과 핵심 흐름을 한 번에 찍은 3분짜리는 인코더가 밀려
중단됐다 — 35B 추론과 4K 무손실 인코딩이 겹친 자리다. 두 촬영으로 나눴다.

사용자가 첫 완성본에서 **확대 구간의 커서가 뚝뚝 끊긴다**고 지적해 고쳤다. 원인은 4배속
자체가 아니라 커서만 4배가 된 것이었다. 앱은 ¼로 흐르는데 커서는 실제 속도였고, 게다가
커서를 바깥에서 한 점씩 보내느라 4K에서 한 칸에 400ms가 들어 18칸에 5초가 걸렸다. 이제
움직임은 페이지 안에서 `requestAnimationFrame`으로 그리고(초당 120번) 실제 마우스는
도착점에서 한 번만 옮긴다. 같은 시나리오 촬영이 **92.2초 → 63.1초**로 줄었고 커서가
촬영 시간을 먹지 않는다. 수치는 [VIDEO-QUALITY](VIDEO-QUALITY.md#앱-데모-촬영)에 있다.

그 촬영에 **대본과 목소리를 얹었다.** 장면 6개의 Claude 초안 대본으로 후보 3벌씩 18벌을
제작 목소리(Qwen3-TTS + `jaeho-ko-r16-v1` 0.60)로 만들고 각 장면 1번 후보로 렌더했다.
**27.2초 완성본**이며 1440p·4K 두 벌, 검증 4/4 통과다.

확인하지 않은 것: **대본도 목소리도 사용자 승인 전이다.** 대본은 Claude 초안이고 1번
후보는 임의로 골랐다 — 검수 화면에서 후보 3벌을 듣고 `voice.selected`를 바꾸면 된다.
내레이션이 4배로 되돌린 그림보다 길어 loop·capabilities·model은 1.75~2.7배로만 되돌아간다
(멈춤 0ms, 그림은 끊기지 않는다). 4배 그대로 보려면 시나리오의 `pause`를 늘려 그림을 더
찍어야 한다. 첫 실행과 핵심 흐름을 한 영상으로 이을지도 정하지 않았다.

사용자가 13~19초 구간이 "딜레이가 심하다"고 지적해 고쳤다. 그 자리는 내레이션이
되돌린 그림보다 길어 **1.75~2.7배로만 되돌아가던** 구간이다(3D가 실제의 0.44배로
흘러 거의 멈춘 것처럼 보였다). 느리게 트는 대신 **그림을 더 찍는** 쪽으로 갔다 —
시나리오의 `pause`를 내레이션 길이 × 4에 맞춰 늘렸다(loop 1.5초 → 8초, capabilities
1.2초 → 5초 셋, model 0.9·1.2초 → 4·8초). 다시 찍은 촬영은 94.3초이고 완성본 28.3초에
모든 장면이 3.63~4.01배로 되돌아간다. 240×135로 재 보면 13·14·15초의 멈춘 프레임이
25장 중 16 → 6장, 16~19초는 거의 0이 됐고 전체 정지 비율은 33% → 23%다. 남은 정지는
투어·채팅 장면(1배)으로, 그 화면 자체가 멈춰 있는 자리다.

## 앱 데모 화면 (2026-09-21)

CLI로만 돌던 앱 데모를 앱의 **앱 데모** 메뉴로 잇고 `./app.sh`에서 쓸 수 있게 했다.
시나리오 고르기 → 촬영 → 장면별 대본 쓰고 확정 → 목소리 후보 만들고 듣고 고르기 →
화질 고르고 완성본까지 한 화면에서 한다. "결과 폴더 열기"로 이미 찍어 둔 결과(CLI로
찍은 것 포함)를 이어 받는다.

화면은 CLI와 **같은 작업자**(`workers/demo.mjs`)를 별도 프로세스로 부른다. 한 가지
일에 두 벌의 구현을 두지 않기 위해서다 — 어느 쪽에서 시작했든 다른 쪽에서 이어갈 수
있다. 대본과 고른 후보는 결과 폴더의 `demo/script.json`이 소유하고 화면은 그 파일을
읽고 돌려 쓴다. 구조는 [ARCHITECTURE](ARCHITECTURE.md#앱-데모-촬영)에 있다.

화면 문법은 앱의 다른 화면과 같은 것을 쓴다 — `record-card`·`field`·`check-row`·
`candidate-gallery`. 처음엔 제 나름의 마크업으로 만들었다가 혼자 겉도는 화면이 돼
사용자 지적으로 다시 짰다. 장면 카드는 대본·확정·찍힌 화면의 글·후보(길이와 재생기)를
한 장에 모은다.

확인한 것: 실제 `./app.sh` 창에서 메뉴가 열리고 preload 다리 8개가 모두 붙었으며,
CLI로 찍은 `rice-first-run` 폴더를 화면이 그대로 읽어 장면 6개·후보 3벌씩·완성본 두
벌·검수 화면까지 잡는다. `npm run check` 통과(앱 385·Python 302).

확인하지 않은 것: 화면에서 촬영·목소리·렌더를 **끝까지 돌려 본 적은 없다**(서비스 검사와
CLI 실행으로 나눠 확인했다). 중지 버튼은 공통 중지 경로를 쓰지만 앱 데모에서 눌러 보지
않았다. 진행률은 단계 이름만 보이고 남은 시간은 없다.

## 첫 실행 영상 시청 뒤 고친 것 (2026-09-21)

**목소리는 승인됐다.** 장면 6개 모두 1번 후보를 쓴다([DECISIONS](DECISIONS.md)). 사용자가
짚은 세 가지를 모두 고치고 다시 찍었다. 지금 결과는 **29.2초**, 1440p·4K 두 벌이다.

**1. 3D가 크게 움직이는 순간의 끊김 → 그 장면만 ⅛로 찍는다.** 촬영이 받는 그림은 능력
모듈 전환에서 초당 5.9장까지 떨어지는데 4배로 되돌리려면 6.25장이 필요하다. `loop`·
`capabilities`를 `timeScale` 0.125로 내리고 `pause`를 내레이션 길이 × 8로 맞췄다
(loop 21초, capabilities 11초씩). 촬영은 94.3초 → **137.6초**, 완성본의 10~24초 구간에서
멈춘 프레임이 25장 중 5~8장 → **사실상 0**이 됐다. 나머지 두 장면은 초당 9~10장이라 ¼
그대로다. 1회성 영상이라 촬영 시간보다 품질을 택한 사용자 판단이다.

**2. 21초의 "채팅 화면이 반짝" → 우리 쪽 결함이었다.** `useDemoAnimationSpeed`가 120ms마다
폴링해 재생 속도를 걸었는데, 4K 부하에서 늦게 걸리면 `updatePlaybackRate`가 이미 지나온
자리를 새 배율로 다시 재어 **애니메이션이 뒤로 되감겼다**. 온보딩 마지막 덮개가 사라졌다
다시 나타났고 그 사이 뒤의 채팅 화면이 비쳤다. 이제 매 프레임(`requestAnimationFrame`)
걸어 되감기는 양이 한 프레임뿐이다. 다시 찍은 원본은 핸드오프 → 채팅으로 한 번에
크로스페이드하고, 완성본에서 한 장만 튀던 이음매(21.84초)가 사라졌다.

**3. 촬영 중 화면이 이상한 것은 정상이다.** 3D는 창 크기·에뮬레이션·촬영 여부와 무관하게
초당 120번 그려진다 — 앱은 느려지지 않는다. 촬영이 받는 그림이 초당 10장인 것은 4K PNG를
보내는 길의 한계다. 창이 왼쪽 아래로 쏠려 보이는 것은 1920×1080 배율 2로 그린 페이지가
1400×900 창에 들어가기 때문이다. 수치와 설명은
[VIDEO-QUALITY](VIDEO-QUALITY.md#앱-데모-촬영)에 있다.

확인하지 않은 것: 새 완성본의 **사용자 시청은 아직이다**(목소리·자막은 승인됐고 대본은
Claude 초안 그대로다). 1440p로 찍으면 스크린캐스트가 몇 장까지 오르는지는 재지 않았다 —
이번에는 4K를 유지했으므로 필요해지면 그때 잰다.

## 화면 정리 (2026-09-21)

사용자 요청 세 가지를 반영했다. 사이드바는 7칸에서 6칸이다 — 텍스트 목소리는 **새로
만들기**의 한 갈래(강의 영상 · 텍스트 목소리)로 들어갔다. 최근 결과는 종류마다 색·아이콘·
종류 표시를 두고 화면 녹화·앱 데모를 따로 거른다. 화면 녹화는 시작하면 고른 모니터에
빨간 테두리를 두르고 3초를 센 뒤 녹화하며, 테두리는 **정지·취소를 누를 때까지** 남는다
(사용자 지정). 앱 안에는 녹화 중인 화면이 1초마다 비친다. 구조는
[ARCHITECTURE](ARCHITECTURE.md#화면-녹화), 규격·측정은
[VIDEO-QUALITY](VIDEO-QUALITY.md#녹화-중-테두리와-미리보기-2026-09-21)에 있다.

테두리는 녹화에 찍힌다(공유 제외 창도 담긴다). 그래서 녹화가 가장자리 8~10px을 바로 안쪽
픽셀로 채워 지운다. 해상도·규격은 그대로지만 그 폭의 화면 내용은 원본이 아니다.

녹화가 끝나면 결과는 녹화 설정 **위**의 결과 카드로 붙고 설정은 그대로 보인다(닫기 가능).
처음에는 완료 화면이 설정을 대신해 사용자가 다시 찍는 길을 찾아 헤맸고, 다른 화면에 다녀와도
완료 화면 그대로라 당황했다.

확인한 것: 내장 화면에서 실제 테두리 → 녹화 → 정지를 돌려 세는 동안 네 변 모두 화면에
빨강, 정지 뒤 0, 녹화 결과 가장자리 빨강 0, 테두리 있음·없음 번갈아 세 번씩 dup/drop 0.
사용자가 실제 앱에서 DELL·내장 화면 모두 테두리가 뜨고 영상에는 담기지 않는 것을 확인했다.
화면 밖(offscreen)으로 띄운 실제 앱에서 세 화면과 녹화 뒤 화면을 찍어 확인했다.
`npm run check` 통과(앱 403·Python 302), 결과 카드 변경 뒤 앱 검사 404 통과.

확인하지 않은 것: 긴 녹화와 움직임이 많은 화면에서 테두리·미리보기와 함께 하는 녹화의
dup/drop(측정은 내장 화면 짧은 녹화뿐이다). 미리보기가 녹화를 늦추는지는 가르지 못해
녹화가 프레임을 놓치면 미리보기가 스스로 멈추게 했다.

## 새로 만들기 통합 (2026-09-21)

사용자와 합의한 대로 **입구는 하나로, 작업 화면은 갈래마다 따로** 뒀다. 사이드바는 6칸에서
4칸(새로 만들기 · 다듬기 · 영상 편집 · 최근 결과)이고, 새로 만들기 위의 탭 한 벌에서 강의
영상 · 텍스트 목소리 · 화면 녹화 · 앱 데모를 오간다. 사이드바의 새로 만들기는 마지막에 본
갈래를 연다. 구조는 [ARCHITECTURE](ARCHITECTURE.md#새로-만들기-화면)에 있다.

작업은 원래 앱 전체에서 한 번에 하나다. 예전에는 강의 제작 중에 앱 데모로 가서 촬영을
눌러야 "이미 실행 중인 작업이 있습니다"를 만났다. 이제 한 갈래가 돌면 다른 갈래는 시작
단추만 막히고(설정·대본은 쓸 수 있다) 탭 옆에 무엇이 도는지와 "보러 가기"가 뜬다. 도는
갈래의 탭과 사이드바의 새로 만들기에 점이 깜박이고 녹화는 빨강이다.

같이 고친 결함: 앱 데모 작업 중 창을 다시 열면 강의 제작 진행 화면에 "실행 중"이 떴다
(복원 코드가 `demo-*` 작업을 몰라 강의로 떨어졌다). 이제 앱 데모 화면이 제 진행을 되살린다.

확인한 것: Playwright로 띄운 실제 앱 창에서 네 갈래 전환, 4칸 사이드바, 최근 결과에 다녀온 뒤
새로 만들기가 앱 데모로 돌아오는 것을 찍어 봤다. 시작 막기·안내·사이드바 표시는 실제
`app.js`를 불러오는 부팅 검사에서 녹화·앱 데모 사건으로 확인했다. `npm run check`
통과(앱 405·Python 302), 전환·사이드바 변경 뒤 앱 407.

확인하지 않은 것: 실제 녹화·강의 제작을 돌리면서 다른 갈래가 막히는 것을 창에서 본 적은
없다(진행 중 모양은 클래스를 직접 붙여 찍었다). 앱 데모 작업 중 창 다시 열기 복원은 검사가
없다.

같은 날 사용 흐름을 다시 검토해 작은 것 넷을 고쳤다(탭 위치는 그대로다). 앱 데모 단계가
끝나도 맥 알림이 뜬다(강의·녹화·편집은 뜨는데 앱 데모만 빠져 있었다). 녹화가 몇 초마다
보내는 사건마다 안내 글을 다시 써 화면 낭독기가 같은 말을 되풀이하던 것을 바뀔 때만 쓴다.
"보러 가기"를 누르면 초점이 그 갈래 탭으로 간다. 창을 최소 폭(980)으로 줄이면 늘 15px 가로
스크롤이 생기던 것(예전부터 있었다: `body` 최소 폭 + 스크롤바 자리)을 없앴다.

사용자 지적으로 화면 전환의 흔들림을 없앴다. 나가는 화면이 4px 올라가고 들어오는 화면이
6px 아래에서 올라와 탭을 옮길 때마다 탭 막대·제목이 위아래로 움직였다. 이제 본문은 제자리에서
글만 바뀌고(90ms 걷고 180ms 올림), 갈래 탭은 따로 떼어 전환 중에도 움직이지 않는다 — 실제
창에서 전환 중 애니메이션을 읽어 이동이 없는 것을 확인했다. 사이드바 아이콘은 유니코드 글자에서
한 벌의 선 아이콘으로 바꿨고, 접으면 44px 칸에 이름이 hover 말풍선으로 뜬다. 음성 설정도 같은
칸으로 접히고 준비 상태 점과 이름·어댑터 말풍선을 남긴다.
강의 영상의 설정 카드만 720px(나머지 셋은 760px)이라 탭을 옮기면 카드 가장자리가 20px씩
들고 났다. 760px로 맞췄고 1440·1200 폭에서 네 화면의 탭·제목·카드 좌표가 같은 것을 쟀다.

남겨 둔 것: 창이 좁으면 막힌 시작 단추가 화면 아래에 있고 이유는 맨 위 탭 옆에만 있다.
좁은 창에서는 안내가 탭 아랫줄로 내려가 제목이 한 줄 밀린다. 다른 갈래 작업이 끝나면
안내는 조용히 사라지고 맥 알림만 남는다.

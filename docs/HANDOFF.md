## 1. 사용자의 목표

한국어 AI Agent 온라인 강의의 대본을 사용자의 목소리로 TTS 생성하고, 기존
자동화가 자막·슬라이드·영상까지 합성하게 한다. 대본이 자주 바뀌므로 원하는
구간만 다시 생성할 수 있어야 하며, 전체 강의와 반복 수정에서 글자당 과금이
생기지 않는 것이 중요하다.

사용자는 먼저 CH01 파일럿으로 품질을 확인하고, 통과한 뒤 범위를 늘리길 원한다.
자막 스타일과 영상 화면 리듬은 이미 별도 파이프라인에서 많이 개선되었다.

## 5. 모델 후보

### 1순위

Qwen3-TTS 1.7B Base를 MLX-Audio로 실행한다.

- 한국어 지원
- 짧은 참조 음성 기반 voice clone
- 재사용 가능한 voice prompt 후보
- Apple Silicon용 MLX 경로

### 비교군

Chatterbox Multilingual V3를 같은 MLX-Audio 환경에서 실행한다.

- 한국어 지원
- 짧은 참조 음성 기반 zero-shot clone
- Qwen과 동일 원문·동일 참조·동일 출력 포맷으로 비교

Fish Speech는 라이선스와 운영 복잡도 때문에 첫 비교군에서 제외했다.

모델과 라이브러리의 최신 라이선스·설치법은 실제 설치 시 공식 저장소에서
다시 확인한다. 과거 검토 시 Qwen3-TTS는 Apache-2.0, MLX-Audio와 Chatterbox는
MIT로 확인했지만 이 문장만으로 상업 이용 결정을 확정하지 않는다.

## 6. 다음 작업의 정확한 범위

1. 공식 설치법과 현재 Apple Silicon 호환 버전을 확인한다.
2. 사용자가 이미 쓰는 Python 3.13.12로 독립 가상환경을 만든다.
3. Qwen3-TTS 1.7B Base와 Chatterbox V3를 설치·다운로드한다.
4. 정제 음성에서 10~20초 참조 후보를 2~3개 고르고 전사문을 맞춘다.
5. CH01의 동일한 30~60초 대본을 두 모델로 생성한다.
6. 생성 시간, 최대 메모리, 오류와 반복을 기록한다.
7. 사용자가 두 파일을 블라인드에 가깝게 듣고 승인한다.
8. 승자만 기존 Node 타임라인 계약에 `local` provider로 연결한다.

첫 작업에서 미세조정, CH01 전체 생성, 전체 7~8시간 생성까지 진행하지 않는다.

## 9. 2026-08-25 현재 구현 상태

섹션 6의 A/B 계획은 완료된 과거 계획이다. 현재 제작 프로필은 Qwen3-TTS 1.7B
Base BF16 + 짧은 참조 음성·전사 + `jaeho-ko-r16-v1` LoRA 강도 `0.60`이다.
Chatterbox V3는 제외했다. `0.60`은 LoRA `1.00`에서 두드러진 사람 발화 노이즈와
과한 AI 특성을 줄여 장시간 강의에 가장 적합하다고 사용자가 승인한 값이다.

강의용 생성기는 `src/local_tts_engine/course_pilot.py`다.

- 같은 슬라이드의 2~4개 스텝, 최대 300자를 한 호흡으로 생성
- 생성 온도 0.75, top_p 0.95
- 앞뒤 무음 정리, 24ms 경계 페이드
- 같은 슬라이드 클립 간격 200ms, 슬라이드 간격 750ms
- 700ms 초과 내부 무음만 480ms로 축소
- `config/production-pronunciation.ko.json`에서 제작용 발음 예외 관리
- Qwen3-ForcedAligner 0.6B 8-bit로 실제 단어 시각 생성
- `export_udemy.py`가 정렬값을 기존 Node 타임라인 계약으로 전달

`udemy-agent/deck/tools/captions.mjs`는 정렬 단어로 SRT/VTT와 화면 자막을
만든다. `capture.mjs`는 다음 스텝 첫 단어 120ms 전에 화면을 전환한다.
Playwright의 가변 녹화 지연은 마젠타 동기 마커 프레임으로 측정해 제거한다.

## 10. 로컬 제작 앱 고도화 (2026-08-26)

Electron 앱에 독립된 `목소리 만들기` 화면을 추가했다.

- 텍스트만 입력해 2~8개 발화 후보 생성
- 전역 설정의 병렬 수에 따라 최대 2개씩 동시 생성
- 후보별 오디오 재생, 하나를 선택해 `selected.wav`로 보관
- 후보와 선택 결과는 `output/voices/<date>/<name>/`에 저장
- 각 후보는 새 시드로 추론하며 기존 오디오 결과를 읽지 않음
- 텍스트 후보의 서로 다른 시드는 비교 선택을 위한 의도적 다양성이다. 강의 TTS는
  고정된 제작 시드와 의미 단위 청킹을 사용하므로 후보 간 편차를 강의 생성의
  불안정성으로 해석하지 않는다.

모델 설정의 이전 버전에는 다음 경로 선택 항목이 있었고 값은 Git에서 제외되는
`artifacts/app-settings.json`에 저장된다.

- 강의 소스 프로젝트
- 내 목소리 원본
- TTS 작업 결과
- 텍스트 목소리 후보
- 자막·타임라인 결과
- 완성 영상 결과
- 참조 음성과 참조 전사문

이 개별 출력 경로 UI는 2026-08-27 단일 `output` 폴더 설정으로 대체됐다.
`udemy-agent`에는 강의 대본·슬라이드 UI와 캡처 실행 코드만 남는다.

앱의 강의 영상 제작은 항상 `course_pilot --no-cache`와 캡처 `--no-cache`를
사용한다. 음성 클립, ForcedAligner JSON, Chromium HTTP 캐시를 재사용하지
않는다. 독립 CLI의 기본 캐시 동작은 이전 호환성을 위해 유지한다.

  후보 수, 병렬 계획, 현재 LoRA 프로필과 감지한 영문 용어를 실시간으로 표시한다.

  줄을 호흡 단위로 보존해 TTS에 전달한다.
- 큰 장식 아이콘과 중앙 정렬 안내문을 제거하고, 낮은 대비의 정보 카드와 짧은

## 21. 검수를 발음 공간으로 옮기고 생성을 조기 종료로 바꿈 (2026-09-03)

### 왜 바꿨나

148페이지가 `지정 발음 불일치`로 실패했지만 음성은 정확했다. Whisper는 소리를
제대로 들었고 자기 표기법으로 적었을 뿐이다.

```
대본 발음: … 왼쪽은 로컬에서 돌리는 이십칠 비, 큐웬삼점육 이십칠비입니다 …
받아쓰기: … 왼쪽은 로컬에서 돌리는 27B, QN 3.6 27B입니다 …
```

받아쓰기를 철자로 비교하는 한 숫자와 모델명이 들어간 페이지는 거의 항상
실패한다. 검수기가 아니라 비교 계층이 틀렸다.

### 발음 공간 비교

`src/local_tts_engine/korean_phonetics.py`가 모든 비교의 기준이 된다.

- 숫자·모델명 정규화와 발음 사전을 양쪽에 적용한 뒤 한글을 자모로 분해한다.
- 전사에 남은 로마자는 한국어 자모음 이름으로 읽는다. `QN` → `큐엔`.
- 현대 한국어가 구분하지 않는 차이만 접는다. 된소리(`ㄲ→ㄱ`)와 `ㅐ/ㅔ` 합류는
  접고, 거센소리는 접지 않는다. `런타임 → 런팀` 같은 오독이 살아 있어야 한다.
- 용어 검사는 부분 문자열이 아니라 Sellers 근사 부분 일치 거리로 판단하고,
  기대 횟수보다 적게 들리면 누락으로 본다.

실측 분리도 (`MAX_PHONETIC_ERROR_RATE = 0.10`):

| 상황 | 철자 거리 | 발음 거리 |
| --- | --- | --- |
| ASR 표기차 (`QN 3.6 27B`, 짧은 청크) | 0.154 | 0.029 |
| ASR 표기차 (실제 148페이지) | 0.048 | 0.009 |
| 긴 문장 안 한 단어 오독 | 0.053 | 0.021 |
| 문장 하나 누락 | 0.487 | 0.480 |
| 절반 날아감 | 0.633 | 0.610 |

철자 거리로는 표기차와 실제 오류가 겹치지만 발음 거리로는 열 배 이상 벌어진다.
그래서 페이지를 실패시키는 관문은 발음 거리를 읽는다.

### 3단 판정

- **통과** — 재시도 없이 다음 청크로 간다.
- **확인 권장(경고)** — 용어가 애매하게 들렸다. 다른 시드로 다시 시도하되,
  끝까지 애매하면 제작은 완료하고 구간만 표시한다.
- **재생성 필요(실패)** — 받아쓰기 불일치, 음성 신호 부족, 과도한 무음,
  클리핑, 발화 속도 이상, 명백한 발음 불일치.

경고가 **모든 시드에서 똑같이 재현되면** ASR 노이즈가 아니라 모델이 일관되게
다르게 읽는 것이므로 실패로 승격한다. 이 경우 같은 조건의 재생성으로는 잘
고쳐지지 않으므로 발음 사전에 항목을 추가하는 편이 빠르다.

1차 판독에서 걸린 청크는 다른 디코딩 온도로 한 번 더 읽고 둘 중 관대한 결과를
취한다. 모든 판독을 견딘 근거만 페이지를 표시할 수 있다.

### 조기 종료 생성

이전에는 위험 청크마다 후보 3개를 **무조건** 만든 뒤 별도 Whisper 단계에서
골랐다. 이제 판독기를 생성기보다 먼저 올려 함께 상주시키고, 청크마다

    생성 → 즉시 받아쓰기 → 깨끗하면 종료, 아니면 다음 시드

로 진행한다. 결과:

- 정상 청크는 생성 1회로 끝난다. 레슨 전체 제작이 크게 빨라진다.
- 대신 **모든** 청크를 검수한다. 발음 사전 용어가 없는 청크의 누락·더듬음도
  잡힌다.
- 정말 안 되는 청크에만 시도를 넉넉히 쓴다 (`--quality-attempts`, 기본 4).
- Metal 메모리는 TTS 약 11.6GB + Whisper 약 1.6GB로 함께 상주한다. 정렬 모델은
  둘을 해제한 뒤 별도 단계에서 올린다. manifest의
  `performance.peakProcessMetalMemoryGb`에 실제 최대치를 기록한다.

청크당 재시도 판단은 `course_pilot.resolve_chunk_take`로 분리해 GPU 없이
단위 테스트한다.

### UX

- 음성 의심 구간은 제작 실패가 아니다. 파일·영상 검증만 제작 성패를 가르고,
  음성 판정은 별도 확인 항목으로 완료 패널과 최근 결과에 실린다.
- 완료 패널과 최근 결과 모두 `2:14–2:21 · 148페이지 · 지정 발음 불일치 · 래그`
  형태로 시간대·페이지·사유·걸린 용어를 보여 준다.
- 구간을 클릭하면 영상 편집의 `목소리 교체 → 페이지에서 새로 생성`이 그 영상과
  그 페이지로 채워진 채 열린다. 음성만 만든 결과는 열 영상이 없으므로 표시만
  하고 클릭을 제공하지 않는다.
- 목소리 후보 카드에 자동 검수 결과를 함께 적어, 귀로 고르기 전에 기계가 무엇을
  들었는지 볼 수 있다.

### 같이 고친 버그

- `trim_and_fade_audio`의 조기 반환 경로가 `shortenedSilenceCount`와
  `shortenedSilenceMs`를 빼고 반환해, 무음이거나 한 프레임보다 짧은 클립에서
  `KeyError`로 런이 죽었다. 게다가 그 불완전한 딕셔너리가 클립 사이드카로
  저장돼 이후 캐시 히트까지 오염시켰다. 네 키를 항상 채우고, 예전 사이드카는
  읽는 시점에 보정한다.
- 완성 영상은 `output/videos/<작업>/`로 옮겨지는데 `timeline.json`은
  `output/projects/<작업>/`에 남았다. 그래서 발행된 영상을 편집에 다시
  올리면 페이지 경계를 잃고, **페이지 범위 목소리 교체가 조용히 전체 음성
  교체로 바뀌었다.** 이제 발행 시 자기 이름의 타임라인(`<영상>.timeline.json`)을
  함께 두고, 예전 결과는 프로젝트 폴더에서 찾아 보완한다.
- 같은 작업 이름을 다시 렌더하면 한 폴더에 여러 mp4가 쌓이는데 `findVideo`가
  사전순 마지막을 골라 **가장 오래된** 파일을 열었다. 수정 시각 기준으로
  바꾸고, 타임라인도 영상별로 짝지어 회차가 섞이지 않게 했다.
- 페이지 타임라인이 없는 영상에 페이지 범위 교체를 시도하면 이유를 밝히고
  멈춘다. 전체 음성을 덮는 것보다 거절이 낫다.
- 후보 생성은 이제 한 번에 하나씩 돌린다. 후보마다 생성기와 판독기가 함께
  올라가므로 병렬 2개는 36GB에서 위험했다.
- 자모 변환이 `str.isdigit()`을 믿어 `①`·`²` 같은 문자를 `int()`에 넘겨
  런 중간에 예외로 죽을 수 있었다. ASCII 숫자만 읽는다.

### 남은 숫자를 읽게 만듦 (실제 강의 전체 검사 후)

기존 코드는 단위가 붙은 숫자(`50개`)와 모델명, 소수만 정규화하고 나머지는 숫자
그대로 TTS에 넘겼다. 넘겨진 숫자는 모델이 마음대로 읽는다 — 사용자가 처음
지적한 `같은 50개라도 → 같은 호십개라도`가 바로 그 결과다.

실제로 만든 31개 매니페스트, 1094개 스텝, 75,766자를 훑어 확인한 결과 그렇게
넘어가던 표현이 **133종**이었다.

```
50이라는 · 160토큰 · 8천 토큰 · 4천억 개 · 15조 토큰 · 40 대 1 · 1, 2, 3, 4.
99% · 10년 · 2026년 8월 · 200페이지 · 10분의 1 · 1등 · 90에서 95로 …
```

`read_remaining_numbers`가 사전까지 적용한 뒤에도 숫자로 남은 것을 한자어 수로
읽는다. 사전이 먼저 돌기 때문에 숫자가 든 사전 항목(`GPT-4o`)은 그대로
우선하고, 글자에 둘러싸인 숫자(`n8n`, `4o`)는 식별자로 보고 두 번 다시 건드리지
않는다. 붙여 읽으므로 조사가 와도(`오십이라는`) 단위가 와도(`백육십토큰`) 자연스럽다.

검사 후 강의 전체에 숫자로 남은 문자는 `n8n`과 `4o` 둘뿐이고, 지정 발음 314건을
원문 표기 그대로의 받아쓰기와 대조했을 때 불일치는 0건이다.

**청취하며 확인해 볼 곳.** 아래처럼 뜻에 따라 고유어와 한자어가 갈리는 단위는
2026-09-04 자연스러움 검사에서도 자동 판단하지 않는다. 어색하면
`config/production-pronunciation.ko.json`에 구체적인 문구를 넣는다(사전이
자연스러움 검사보다 먼저 돈다).

## 22. 한국어 자연스러움 사전검사 (2026-09-04)

148페이지에서 실제 음성은 `방금 본 십 개, 백 개, 천 개`였고 Whisper는 이를
`10개, 100개, 1000개`로 적어 통과시켰다. 당시 기대 발음문부터 `십 개`였으므로
Whisper 오검출이 아니라 생성 전 언어 판단의 누락이었다.

`src/local_tts_engine/korean_naturalness.py`를 발음·숫자 정규화 앞에 추가했다.

- `개·명·가지`의 1~99는 고유어 관형형으로 만든다. `10개 → 열 개`,
  `20개 → 스무 개`, `34개 → 서른네 개`다.
- 100 이상은 기존 한자어 규칙이 처리한다. 따라서 `100개 → 백 개`,
  `1000개 → 천 개`다.
- 사용자가 이미 승인한 `50개 → 오십 개`는 제작 예외로 보존한다.
- `6개월`의 `개`를 물건 수량으로 오인하지 않으며, `번·장·시간`처럼 문맥이
  필요한 단위는 자동 변환하지 않는다.
- 발음 사전은 자연스러움 검사보다 먼저 적용하므로 더 구체적인 강의 문구가 일반
  규칙을 덮어쓸 수 있다.
- 검사 결정은 각 엔트리와 manifest의 `naturalness`에 남기고 앱의
  `validation-report.json`에도 전달한다.

실제 CH02 전체 대본을 정적으로 검사했을 때 148페이지의 3번 스텝은
`열 개, 백 개, 천 개`가 됐다. 강의 전체에서 이 계층이 관여한 엔트리는 16개다.
새 음성 생성은 하지 않았으므로 다음 148페이지 재생성에서 최종 청취 확인한다.

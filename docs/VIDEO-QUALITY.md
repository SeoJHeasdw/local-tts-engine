# 영상 규격과 검증 근거

현재 촬영·편집 계약과 2026-09-10·09-18·09-20 측정 근거다. 짧은 시험의 수치를 실제 강의
전체의 화질·성능 보증으로 확대하지 않는다. 음성 검수는 [QUALITY](QUALITY.md)를 따른다.

## 제작 규격

| 앱 표시 | CLI ID | 렌더·출력 |
| --- | --- | --- |
| 초고화질 · 4K | ultra | 3840×2160 |
| 고화질 · 1440p | high | 2560×1440 |
| 기존 해상도 · 1080p | standard | 1920×1080 |

앱 새 작업은 high가 기본이며 선택을 저장한다. 과거 CLI·이어하기 기록의 누락된
옵션은 standard로 해석한다. 세 단계 모두 PNG 입력 → libx264 slow/CRF 16,
25fps, yuv420p, BT.709 limited다. 1080p도 중간 손실 압축을 거치지 않는다.

논리 캔버스는 1920×1080이며 실제 뷰포트와 자막을 출력 크기에 맞춘다. 받은 PNG의
크기와 Stage가 뷰포트를 채우는지 검사한다. 4K 요청에 1080p 프레임이 오면 확대해
통과시키지 않는다. RGB→YUV 변환과 색 태그를 모두 BT.709로 명시한다.

1440p는 4/3배여서 1px 선이 분수 픽셀에 놓일 수 있다. 픽셀 수를 체감 선명도나
파일 크기 배율로 해석하지 않는다. 60fps·HDR·10비트 제작을 지원한다고 표시하지 않는다.

## 프레임·실패 처리 계약

- 출력 시각 이전의 마지막 프레임을 선택한다. 미래 프레임을 앞당기지 않는다.
- PNG 완료 순서와 촬영 순서는 다를 수 있어 CDP 시각으로 정렬한다. 이미 출력한
  시각보다 오래된 프레임도 ACK는 보낸다. 150ms를 넘는 역전은 시계 오류로 중단한다.
- ACK는 출력 프레임 간격의 0.75배로 배분한다(25fps에서 30ms). 화면을 고르게
  받기 위한 간격이며 임의 프레임 폐기나 화질 하향으로 처리량을 줄이지 않는다.
- 촬영 브라우저는 `playwright@1.62.0`(Chromium 1234)으로 **고정**한다. 위 ACK 간격은
  이 판본에서 측정한 값이라 브라우저를 올리면 결과가 달라진다. 2026-09-18에 1.63.0
  (Chromium 1243)으로 재보니 4K에서 받는 프레임이 3초 시험 기준 95개에서 65개로
  줄고 복제 프레임이 5~6개에서 41~47개로 늘었다(각 3회). 1080p·1440p는 거의 같았다.
  코드는 같았고 브라우저 판본만 달랐다. 올릴 때는 `npm run check:capture`로 세 화질을
  다시 재고 이 문단의 수치를 갱신한다. 판본만 보고 통과시키지 않는다.
- 첫 프레임·준비 타임아웃, 연결·ACK 실패, 시각 누락, 인코더 조기 종료를 전파한다.
  입력 적체 512MiB, 대기 프레임 256MiB/64개 상한을 넘으면 같은 화질로 재시도한다.
  이는 전체 FFmpeg 메모리 제한이나 4K 실시간 성능 보증이 아니다.
- 프레임 수는 올림해 마지막 음성을 덮는다. 합성 길이는 프레임수/fps로 정하고
  `-shortest`로 마지막 프레임을 자르지 않는다. 영상은 음성보다 최대 한 프레임 길 수 있다.
- 촬영 중 일시정지는 현재 편 뒤에 처리한다. SIGSTOP으로 촬영 시계를 멈추지 않는다.
- 화질·자막 옵션의 정확한 파일명, 실제 크기·프레임 수·fps·색·코덱·음성·길이를 확인한다.
  영상별 `.capture.json`의 SHA-256·소스 판본도 검증한다. 없는 파일을 옛 MP4로 대체하지 않는다.

촬영 보고서는 프로필·프레임 수신/복제·정렬·적체·실제 스트림과 삽입 자료의 원본
해상도를 기록한다. 새 작업은 기존 완료본을 건너뛰지 않는다. 명시적 이어하기도
파일·화질·판본·해시가 확인된 레슨만 건너뛴다.

## 편집·보존 계약

- 규격·스트림 헤더·시간 단위가 같은 전체 클립은 스트림 복사한다. 전체 MP4 하나는
  원본을 복사한다. 페이지 음성 교체도 화면 길이가 같으면 영상 스트림을 유지한다.
- 자르기·서로 다른 규격의 합치기는 가장 큰 입력 크기(최소 1080p)에 맞춰 정규화한다.
  재인코딩은 slow/CRF 16이며 입력 fps·SAR·화면 비율을 보존한다. 30fps를 25fps로 바꾸지 않는다.
- 재인코딩에서 보존하지 못하는 HDR·10비트·4:4:4·wide-gamut/full-range는 거절한다.
  기존 완성본을 덮어쓰지 않으며 성공한 실행의 중간 MP4만 정리한다.
- 저해상도 삽입 자료의 정보량은 출력 해상도를 높여도 늘지 않는다. img/video/canvas의
  원본·표시 크기는 교체 검토 자료이며 자동 불합격이 아니다.
- 재인코딩된 영상이나 음성을 픽셀·PCM 100% 동일이라고 설명하지 않는다. 영상 스트림
  복사도 음성 편집의 AAC 재압축과는 별개다. 동일성은 실제 해시로 확인한다.

## 화면 녹화

디스플레이 하나를 **소스 해상도 그대로** 녹화한다. 화질 선택·확대·축소·크롭은 없고,
yuv420p가 받지 못하는 홀수 크기 화면은 녹화하지 않는다. avfoundation `bgr0` 입력,
25fps, 커서 포함이며 인코딩은 덱 촬영과 같은 `captureEncodingArgs`(slow/CRF 16,
RGB full → BT.709 limited)다. 손실 압축은 1회다.

1. 영상만 녹화한다. 정지는 ffmpeg stdin의 `q`다. SIGINT로도 파일은 남지만 종료 코드가
   255라 실패와 구별되지 않는다. 진행의 frame·dup·drop은 `-progress`로 받는다.
2. 녹화된 영상 길이에 맞춰 무음 AAC(LC·48kHz·모노·192k)를 붙인다. 영상은 복사한다.
   편집이 음성 없는 영상을 거절하고, 무음을 녹화와 동시에 만들면 음성이 먼저 끊긴다.

검증은 영상 규격(크기·코덱·색·프레임 수 = 올림(길이×25)), 음성 형식, 음성 트랙 길이,
**담긴 소리 길이**(AAC 프레임 수×1024 ÷ 48000)가 영상 길이와 100ms 안인지 본다.
dup·drop이 0이 아니거나 정지 전에 끝나면 완료로 두되 `warnings`에 남기고 최근 결과에
경고로 표시한다. 못 따라가는 화면이 생기면 무손실 중간 녹화 뒤 한 번 인코딩하는
방식을 검토한다. 화질을 낮춰 해결하지 않는다.

| 측정 (M4 Max, macOS 26.7, ffmpeg 8.1.1) | 결과 |
| --- | --- |
| 60초, 내장 3456×2234·DELL 1920×1080 (설계 측정) | 두 화면 모두 1500프레임·60.000초·dup/drop 0 |
| 빠른 스크롤 오프라인 인코딩 (설계 측정) | 어두운 IDE 3456×2234 1.35x, 사진 배경 1080p 0.914x(미달) |
| 앱 경로 10초 DELL 녹화·SIGUSR1 정지 | 265프레임, 영상·음성 모두 10.600초, dup/drop 0 |
| 덱 1080p(`check:capture`)와 스트림 서명 | 영상 SPS/PPS·time_base 1/12800, 음성 AAC 해시까지 동일 |
| 녹화 → 구간 교체(keep-video) → 덱과 합치기 | 영상 복사 유지, 합치기가 "다시 굽지 않고" 이어 붙임(75+265프레임) |
| 마이크 포함 10초 | 트랙은 10.609초지만 담긴 소리는 9.19초(약 13% 누락). 마이크만 5초도 4.46초 |
| 그 녹화에 내레이션 구간 교체 | 내레이션이 최대 약 0.7초 밀림. 무음 트랙 녹화는 정확히 제자리 |

인코딩 속도는 해상도보다 화면 내용이 좌우한다. 짧은 측정이므로 15분 녹화의 보증으로
쓰지 않는다. 마이크 누락은 ffmpeg avfoundation이 음성 버퍼를 한 칸만 두어 생기는 것으로
보이며(빈틈이 정확히 512샘플 단위), 이 Mac에서 음성 포함 녹화는 검증에서 걸린다.
구간 음성 교체는 녹음된 소리를 구간 안에서 지우고 내레이션으로 **대체**하며 구간 밖의
소리는 남긴다. 한 번에 바꿀 수 있는 구간은 120초까지다. 위 녹화·마이크·구간 교체·합치기의
파일과 스크립트는 `output/reviews/2026-09-18/screen-recording/`에 있다.

합치기가 복사로 끝나는 조합은 1080p 녹화와 덱 standard다. 클립을 잘라 합치면 전부
다시 인코딩하고, 16:9가 아닌 내장 화면 녹화를 16:9 덱과 합치면 레터박스가 생긴다.
1440p 녹화와 덱 high의 서명 일치는 확인하지 않았다.

## 앱 데모 촬영

앱 창을 CDP 스크린캐스트로 받는다. 창 크기로는 1920×1080을 만들 수 없어(내장 화면
작업 영역에 막혀 1920×1006) `Emulation.setDeviceMetricsOverride`로 CSS 1920×1080 ·
배율 2를 준다. 레이아웃은 1080p 그대로이고 프레임은 정확히 3840×2160 PNG로 온다.

손실 압축은 한 번이다. 촬영은 `libx264rgb -qp 0 -preset veryfast`로 색 변환 없이 받아
`demo/raw.mkv`에 남기고, 색 변환(`CAPTURE_COLOR_FILTERS`)과 H.264는 편집을 모두 적용한
뒤 렌더가 한 번만 한다. 덱 촬영·화면 녹화와 같은 색 경로·음성 서명(AAC LC 48kHz 모노
192k)이라 합치기가 다시 굽지 않는다. 출력 기본은 1440p다 — 확대 구간이 4K 원본에서
잘리므로 1440p에서 또렷하고 덱 기본과 같다.

`recorder.finish({ endAt })`은 앱 데모용이다. 끝나는 시각을 찍고 나서야 알기 때문에
`begin`에는 시나리오 제한 시간으로 넉넉한 상한을 주고 실제 끝 시각에서 끊는다. 주지
않으면 지금까지처럼 `begin`에서 정한 수까지 마지막 화면을 채운다(덱 촬영은 그대로다).

렌더는 ffmpeg 한 번이다. 설계의 구간별 `trim`→`concat` 대신 시간축을 한 번 접는다:
`setpts`가 구간마다 기울기를 바꾸고 멈출 자리에서 시간을 건너뛰면 `fps`가 그 빈자리를
마지막 화면으로 채운다. `split`으로 갈라진 가지가 자기 차례를 기다리며 프레임을 쌓는
문제(4K 무손실에서 기가바이트 단위)를 피하려는 것이고, 결과는 같으며 원본은 한 번만
지나간다. 검증은 규격·**프레임 수 = 계획 길이**·음성 길이·내레이션이 영상 안에 드는지다.

| --- | --- |
| 언어 선택 화면 4K 6초 | 137프레임 수신, 복제 24/150, 최장 정지 2프레임 |
| 채팅 핵심 흐름 4K 30초 | 947프레임 수신, 복제 49/750, 최장 정지 8프레임 |
| 3D 시네마틱 10초 · 1080p / 1440p / 4K | 복제 23 / 77 / 158 (250칸). 4K는 초당 약 9장이라 끊겨 보인다 |

### 느리게 찍어 되돌리기 (2026-09-21, 첫 실행 촬영)

4K에서 3D는 초당 9~12장밖에 그리지 못한다. 그 장면을 앱의 데모 모드로 **¼ 속도**로
찍고 편집이 **4배로 되돌리면** 촬영이 받은 서로 다른 그림이 모두 완성본에 쓰인다.
서로 다른 그림의 수는 `ffmpeg -vf mpdecimate`로 센다.

| 측정 (M4 Max, 4K 촬영 92.2초) | 결과 |
| --- | --- |
| 촬영 원본의 각성 26.9초 | 673프레임 중 서로 다른 것 319 = **초당 11.9장** |
| 완성본 4K의 같은 구간 6.7초 | 168프레임 중 서로 다른 것 161 = **초당 24.0장** |
| 완성본 1440p의 같은 구간 | 168프레임 중 157 = 초당 23.4장 |
| 촬영 전체 | 2304프레임, 복제 1439, 인코더 백로그 최대 5MB / 512MB |

**커서는 페이지 안에서 그린다.** 4K 촬영 중 CDP 왕복 한 번이 `page.mouse.move` 192ms,
`page.evaluate` 195ms, 둘 다 401ms다(각 20회 측정). 한 점씩 바깥에서 보내던 예전 방식은
18칸 이동에 5초가 걸렸고, 4배로 되돌리면 1.25초 동안 18자리만 지나 뚝뚝 끊겨 보였다 —
확대 구간에서는 움직인 거리가 1.6배로 보여 더 두드러진다. 같은 페이지 안의
`requestAnimationFrame`은 초당 120번 돈다. 그래서 움직임은 페이지가 그리고 실제 마우스는
도착점에서 한 번만 옮긴다. 같은 시나리오의 촬영이 207.9초에서 **63.1초**로 줄었다
(칸을 네 배로 늘렸던 중간 판이 207.9초, 예전 방식이 92.2초다).

**촬영 길이의 한계.** 온보딩과 핵심 흐름을 한 번에 찍은 3분짜리는 `result` 장면에서
인코더가 실시간을 따라가지 못해 중단됐다. 그 장면은 Ollama가 35B 모델을 돌리는 동안
화면이 멈춰 있던 구간이다 — 같은 Mac에서 4K 무손실 인코딩과 큰 모델 추론이 겹치면
x264가 밀리는 것으로 본다(백로그 512MB 상한). 추론이 없는 92초 촬영은 최대 5MB로
여유가 컸다. 그래서 첫 실행과 핵심 흐름을 두 촬영으로 나눈다. 성공한 촬영도
`scenes.json`의 `frames.peakBacklogBytes`에 여유를 남긴다.
| Electron 44 + playwright 1.62 `_electron` | 픽스처 앱 기동 0.82초, 에뮬레이션에서 `page.mouse`는 CSS px |
| RICE 파일럿 2회 (2026-09-20) | 76.2초/1904프레임(복제 238)과 55.0초/1374프레임(복제 156). 렌더는 각각 26.0초·20.7초 |

`zoompan`은 자를 위치와 크기를 **입력 픽셀 단위 정수로 내림**한다. 2026-09-20에 4K 격자
입력의 출력 프레임에서 실제 쓴 값을 역산해 확인했다(측정−이상 최대 1.2px / 0.6px).
입력이 RGB라 yuv420p의 짝수 내림은 걸리지 않는다. 1440p 출력에서 확대 중심의 위치 오차는
최대 약 1.2px이고, 프레임 간 떨림은 설계 움직임(0.6초에 1.0→1.6배)에서 최대 0.85px로
그 구간의 프레임당 이동 4~42px에 묻힌다. 확대를 유지하는 구간은 값이 상수라 떨림이 없다.
3초에 1.0→1.15배처럼 느린 크리프에서는 떨림이 이동과 같은 크기가 되므로 확대 전환을
1.5초보다 길게 늘이지 않는다. 대조 영상과 스크립트는
`output/reviews/2026-09-20/app-demo-build/`에 있다.

커서는 **우리가 보낸 좌표**로 그리고, Electron 창은 촬영 중 `setIgnoreMouseEvents(true)`로
둔다. 첫 RICE 파일럿에서 화살표가 입력창이 아니라 엉뚱한 빈 공간에 찍혔는데, 창 위에 놓여
있던 실제 마우스의 `mousemove`를 오버레이가 따라갔기 때문이다(오버레이 DOM·좌표는 정상이었고
`page.screenshot`에서는 제자리였다). CDP로 보내는 조작은 OS 히트 테스트를 거치지 않아
무시 설정과 무관하게 그대로 들어간다. 웹 화면은 headless로 띄워 같은 문제를 피한다.

3D 시네마틱을 4K로 넣는 방법, 빨리 감기 최대 배율(시작값 4배), 자막을 영상에 굽는지는
파일럿 영상을 보고 정한다. 짧은 픽스처 촬영의 수치를 실제 앱 데모의 보증으로 쓰지 않는다.

## 인코딩 비교 근거

기존 경로는 CDP JPEG(기본 quality 90) → VP8(목표 1Mbps, realtime/speed 8) →
H.264 fast/CRF 18이었다. 과거 CH01·CH02 표본의 영상 비트레이트는 약 0.52~0.63Mbps였다.
비트레이트는 진단 자료이며 합격 하한이 아니다.

저장된 브라우저 PNG 6장을 각 3초, 총 18초/450프레임으로 재생해 실제 제작 인코더를
비교했다. 기존 설정 재현은 PNG→VP8→H.264여서 선행 Chromium JPEG 손실은 제외했다.

| 측정 | 기존 설정 재현 | 새 1080p |
| --- | ---: | ---: |
| RGB MSE | 5.883 | 4.337 (26.3% 감소) |
| RGB PSNR | 40.43dB | 41.76dB |
| RGB SSIM | 0.98759 | 0.99119 |
| 파일 크기 | 1,051,578 bytes | 1,464,689 bytes |

후속 안전성 수정 뒤에도 이 450프레임의 디코딩 해시·파일 크기는 동일했다.
Pillow JPEG 입력까지 넣은 별도 대조에서는 MSE 45.1% 감소였지만 Chromium JPEG와
픽셀 동일성을 검증하지 않았으므로 실제 강의 개선율로 쓰지 않는다.
RGB 전체 지표를 체감 화질 백분율로 해석하지 않는다. 실제 1440p/4K 웹 렌더의
원본 대비 개선율은 미측정이며, 파일 프레임 공급 실험의 속도는 브라우저 성능이 아니다.

근거: `output/reviews/2026-09-10/video-quality/comparison/`의
`run-comparison.mjs`, `jpeg-control.mjs`, `analyze.py`, `metrics.json`, 비교 MP4·PNG.
초기 파일 측정은 상위 `video-quality/`에 있다.

## 촬영 회귀의 측정 근거

| 문제·입력 | 관측과 수정 후 결과 |
| --- | --- |
| 1440p PNG 전송 순서 | 0.70~0.82ms 뒤바뀜을 오류로 보던 6초 촬영은 6회 중 3회 중단. 시각 정렬 후 6/6 성공 |
| 4K 프레임 도착 뭉침 | 3초/75프레임에서 ACK 즉시일 때 복제 36~40개, 30ms 간격 뒤 2~10개. 같은 시험의 전환 시각 유지 |
| 세 해상도 촬영 | 짧은 합성 화면을 연속 3회씩 실행해 9/9 통과 |
| 음성 320150ms | 8004프레임 필요. 음성 길이의 `-t`와 `-shortest`가 8003개로 자름. 프레임 수 기반 합성 후 8004개 |
| 소수 길이 실제 촬영 | 3150ms를 1440p·4K로 촬영해 각각 79프레임/3160ms 확인 |

전송 순서·ACK·소수 길이 회귀는 `tests/electron/capture-encoding.test.mjs`와
`scripts/check_capture.mjs`에 있다. 320150ms 확인은 작은 화면으로 같은
프레임 수를 합성한 검사다. 사용자의 320초 4K 레슨 전체를 다시 촬영한 근거가 아니다.
측정 기기의 PNG 처리량은 약 105MB/s였고 4K 복제가 0은 아니었다. 빠른 모션의 긴
4K 강의 성능·품질은 이 짧은 측정으로 보증하지 않는다.

재현 명령은 `npm run check:capture -- --output <새 경로>`다. 이 기록을 새 실행
지시로 해석하지 않는다. 실제 강의 시청 승인과 합성 화면 회귀 검사는 구분한다.

## 무손실 용량 절감의 측정 근거

불필요한 재압축 회피가 현재 적용한 절감이다. 원본·완성본을 자동 정리하지 않는다.

# 영상 화질 진단과 제작 계약

2026-09-10. 대상은 udemy-agent의 화면 촬영부터 이 앱의 검증·편집까지다.
강의 내용·연출·음성 프로필을 다시 평가하거나 변경하는 작업은 아니다.

## 평가

사용자의 문제는 기존 영상의 가독성 상실이 아니라, 모니터에서 보는 웹 원본과
완성 영상 사이의 큰 선명도 차이다. 현재 완성본은 1920×1080·25fps이며,
고품질 제작 원본과 비교할 때 줄여야 할 손실을 평가한다.
현재 설치된 Playwright 코드에서 확인한 기존 경로는 **CDP JPEG(기본 quality 90)
→ FFmpeg VP8(목표 1Mbps, realtime/speed 8) → H.264 fast/CRF 18**이다.
중간 압축 손실과 1080p 출력 해상도를 각각 분리해서 평가해야 한다.
최종 CRF만 낮추거나 완성 MP4를 4K로 확대해도 중간에 잃은 세부는 돌아오지 않는다.

실제 파일의 FFprobe 측정:

| 대상 | 규격 | 평균 영상 비트레이트 |
| --- | --- | ---: |
| 9월 9일 CH01 전체 MP4 | H.264 / 1080p / 25fps | 0.580 Mbps |
| 같은 CH01의 중간 capture.webm | VP8 / 1080p / 25fps | 약 0.850 Mbps¹ |
| 9월 9일 CH02 L02 MP4 | H.264 / 1080p / 25fps | 0.522 Mbps |
| 같은 L02의 중간 capture.webm | VP8 / 1080p / 25fps | 약 0.782 Mbps¹ |
| 9월 10일 CH02 L02 (2) MP4 | H.264 / 1080p / 25fps | 0.626 Mbps |

¹ WebM은 영상만 있는 컨테이너의 평균값. MP4는 음성을 제외한 영상 스트림 값이다.
비트레이트는 진단 증거이며 점수나 합격 하한이 아니다. 정적인 어두운 화면은
선명해도 작은 파일로 압축될 수 있다. CH02 L02 (2)의 35초 프레임도 직접 확인했다.

측정 정본과 확인 프레임은
`output/reviews/2026-09-10/video-quality/`에 있다. 과거 완성본의 전체 시청이나
새 브라우저 원본과의 비교를 수행한 것은 아니다. 아래 별도 재현 실험은 저장된
브라우저 PNG를 사용한 인코딩 비교다. 작업 시작 시 덱에 PNG 스크린캐스트·slow/CRF 16으로
바꾸는 미커밋 수정이 이미 있었고, 이를 보존·확장했다. 그 선행 변경을 이번 작업의
독자적인 성과로 계산하지 않는다.

## 실제 인코딩 비교 (2026-09-10 후속)

저장된 브라우저 PNG 6장(설계 요약·인계/도구·영문 문서·외부 도해·업무 문서·모델
선택)을 각각 3초씩, 1080p·25fps·총 18초/450프레임으로 동일하게 재생했다.
새 영상은 실제 `captureEncodingArgs()`와 `startScreencastEncoder()`를 import해
생성했다. 브라우저 프레임 공급만 파일 재생기로 대체했고, PNG→FFmpeg 파이프·
프레임 선택·최종 H.264 인코딩 코드는 제작 코드 그대로다. 개인 음성은 생성하지 않았다.

| 측정 | 기존 설정 재현¹ | 개선 코드 1080p | 차이 |
| --- | ---: | ---: | --- |
| 원본 대비 RGB MSE (낮을수록 좋음) | 5.883 | 4.337 | **26.3% 감소** |
| RGB PSNR (높을수록 좋음) | 40.43 dB | 41.76 dB | +1.32 dB |
| RGB SSIM (높을수록 좋음) | 0.98759 | 0.99119 | +0.00360 |
| 파일 크기 | 1,051,578 bytes | 1,464,689 bytes | +39.3% |

¹ 기존 설정 재현은 PNG→VP8→H.264다. 브라우저의 선행 JPEG 손실을 제외한
보수적인 비교이며 실제 과거 MP4의 픽셀을 재현했다고 주장하지 않는다.
장면별 MSE 감소는 약 14.6~38.9%다. 전체 450프레임의 RGB 오차를 평균했으며
PSNR dB를 단순 평균하지 않았다. 휘도만 측정하지 않아 색 글자·선의 손실도 포함한다.
어두운 빈 배경이 많은 덱의 전체 지표이므로 지표를 체감 화질 백분율로 해석하지 않는다.

추가 시험에서는 JPEG quality 90/4:4:4 입력까지 넣었을 때 RGB PSNR이 39.15dB,
SSIM이 0.98158이었다. 이 시험 대비 새 코드의 MSE는 **45.1% 감소**했다.
다만 이 JPEG는 Pillow로 생성했으며 Chromium JPEG와 픽셀이 같다고 검증하지
않았으므로, 45.1%를 실제 강의 전체의 개선율로 쓰지 않는다.

원본/기존 재현/개선 PNG를 같은 좌표로 자르고 최근접 보간으로 2배 확대해 직접
확인했다. 개선본은 가는 색 테두리를 원본에 더 가깝게 보존했다. 큰 글자나 이미
원본이 흐린 문서 이미지에서는 변화가 작았다. 압축 개선 효과는 확인됐지만,
1080p 개선만으로 모니터 웹 원본과의 격차가 완전히 해소됐다는 판단은 하지 않는다.

근거는 `output/reviews/2026-09-10/video-quality/comparison/`의
`run-comparison.mjs`, `jpeg-control.mjs`, `analyze.py`, `metrics.json`, 프레임별
PSNR/SSIM 로그, 비교 MP4와 `comparison-before.png`에 있다. 4K를 1080p PNG의
단순 확대로 흉내 내지 않았으며, **실제 1440p/4K 웹 렌더의 개선율은 미측정**이다.
프레임 공급이 실시간 브라우저가 아니므로 이 실험의 실행 속도·적체를 촬영 성능으로
보고하지 않는다. 참고 원본 RGB 영상은 입력 PNG에서 재현할 수 있는 임시 파일이다.

브라우저 접근 문제는 이후 사용자가 중단하도록 요청했다. 이 작업에서 새 브라우저
접근이나 4K 실시간 촬영을 재시도하지 않는다. 후속 검수는 코드·제어된 프레임 입력·
실제 FFmpeg를 대상으로 하며, 실제 4K 웹 렌더의 시청 승인을 대신하지 않는다.

## 세 단계

| 앱 표시 | CLI ID | 실제 렌더·출력 | 1080p 대비 픽셀 수 |
| --- | --- | --- | ---: |
| 초고화질 · 4K | ultra | 3840×2160 | 4배 |
| 고화질 · 1440p | high | 2560×1440 | 약 1.78배 |
| 기존 해상도 · 1080p | standard | 1920×1080 | 1배 |

새 앱 작업 기본값은 high이며 선택을 기기에 기억한다. 과거 CLI 명령과 이미
저장된 이어하기 작업은 누락된 옵션을 standard로 해석한다. 앱·CLI 계약은
`tests/electron/video-quality.test.mjs`에서 대조한다.

세 단계 모두 무손실 PNG 입력 → libx264 slow/CRF 16, yuv420p, BT.709 limited,
25fps다. 기존 해상도 옵션도 중간 압축은 제거한다. 품질 차이는 주로 실제 렌더
해상도이며 CRF를 올려 기존 옵션을 일부러 흐리게 만들지 않는다. 픽셀 수 배율을
체감 화질·파일 크기 배율로 해석하지 않는다. 레슨마다 실제 파일 크기를 확인한다.
25fps를 유지하므로 60fps의 움직임 개선을 약속하지 않는다.
1440p는 논리 캔버스의 4/3배여서 1px 선이 분수 픽셀 경계에 걸릴 수 있다.
모든 선이 무조건 더 또렷하다고 보증하지 않으며, 세부 선명도를 우선할 때는
정수 2배인 4K를 먼저 비교한다. 1440p 기본값은 구현 선택이고 사용자 시청 승인은 아니다.

## 화면과 색, 시간

- 덱의 논리 캔버스·글자 크기 규칙은 1920×1080이다. 브라우저 뷰포트를 실제
  출력 크기로 키우고 기존 Stage가 전체 비율을 맞춘다. 자막도 같은 논리 캔버스에서
  확대하여 크기·하단 여백·두 줄 폭을 함께 유지한다.
- 받은 PNG 헤더의 실제 크기를 검사한다. 요청이 4K인데 1080p 프레임이 오면
  확대하거나 성공으로 표시하지 않고 중단한다. Stage가 뷰포트를 채우는지도 검사한다.
- RGB→YUV의 행렬을 BT.709로 실제 변환하고 태그도 일치시킨다. FFmpeg에서
  출력 옵션만 지정하면 색 원색·전달함수 태그가 빠지는 현상을 재현해 프레임의
  setparams도 명시했다. 이것은 SDR 제작 경로이며 HDR/10-bit 지원은 아니다.
- 프레임은 목표 시각 **이전의 마지막 화면**을 선택한다. 가까운 미래 프레임을
  선택하면 정적인 장면에서 전환이 일찍 보일 수 있다. 희소한 PNG 갱신으로 이
  문제를 재현하고 실제 인코딩 결과에서 400~480ms의 번쩍임 위치를 검사한다.
- 브라우저는 PNG 인코딩을 병렬로 돌려 **완료 순서대로** 프레임을 보낸다. 1ms도 안 되게
  떨어져 찍힌 두 프레임이 뒤바뀌어 도착하므로, 도착 순서가 아니라 프레임 자신의 시각으로
  자리를 잡는다. 이미 기록한 프레임보다 오래된 프레임은 어떤 출력 시각도 이길 수 없어
  버리되 확인 응답은 보낸다. 자세한 내용은 아래 '프레임 도착 순서' 절에 있다.
- 확인 응답은 한 출력 프레임의 0.75배 간격으로 띄워 보낸다. 브라우저가 화면을 두세 장씩
  몰아 잡고 멈추는 것을 막아 출력 슬롯을 고르게 채운다. 아래 '4K 프레임 굶주림' 절에 있다.
- 첫 프레임/준비 명령 타임아웃, FFmpeg 조기 실패 전파, 512MiB 입력 적체,
  256MiB/64개 대기 프레임 상한을 둔다. 연결·ACK 실패, 시각 누락과
  준비 완료 전의 인코더 정상 종료도 실패로 처리한다. 되돌릴 수 있는 지연(150ms)을
  넘는 시각 역전은 시계 자체가 움직인 것으로 보고 중단한다. 미래 프레임을 앞당기거나
  버퍼가 넘친 화면을 버리지 않는다. 시각이 불명확하면 최신 프레임으로 물러서지 않는다.
  초과하면 같은 화질의 재시도를 안내한다. 몰래 해상도·CRF·모션을 낮추지 않는다.
  이 상한은 FFmpeg 전체 프로세스 메모리 제한이나 4K 실시간 성능 보증이 아니다.
- 완성 MP4의 크기·프레임 수·프레임률·색 정보·길이를 확인한 뒤 기존 결과를
  교체한다. `capture-report.json`에 프로필·프레임 수신/복제·적체·실제 스트림과
  소스 해상도 한계를 남기고 앱 검수 기록에도 보관한다. 영상별 `.capture.json`과
  SHA-256을 함께 남겨 앱이 현재 화질·자막 파일의 무결성과 판본을 확인한다.
- 필요한 프레임 수는 올림하여 마지막 음성 구간을 덮는다. 촬영 중 일시정지는
  현재 편이 끝난 뒤 처리한다. 시스템 시계의 큰 변화는 동기화 실패로 중단한다.

## 편집과 원본 소스의 한계

규격과 스트림 헤더·시간 단위가 같은 전체 클립은 복사한다. 자르거나 서로 다른
규격을 합칠 때는 가장 큰 입력의 너비·높이를 유지하여 정규화한다(최소 1080p).
서로 다른 규격에서는 모든 구간의 색·시간 단위·오디오 채널도 맞춰야 하므로
전체 클립을 다시 인코딩할 수 있다. 저해상도 입력만 확대되는 부분의 세부가
새로 생기는 것은 아니다. 편집 재압축도 slow/CRF 16을 사용한다.
음성 교체에서 화면 길이가 그대로면 기존처럼 영상 스트림을 복사한다.
재인코딩을 거치는 편집은 완성본과 픽셀이 100% 같다는 기능이 아니다.
전체 MP4 하나는 입력 해상도·코덱을 그대로 복사한다. 재인코딩에서 보존할 수 없는
HDR·10비트·4:4:4·wide-gamut/full-range 입력은 자동 다운그레이드하지 않고 거절한다.
30fps 입력의 음성 교체도 25fps로 강제하지 않는다. 정규화는 SAR을 반영해
영상 비율을 유지하고, 완료 후 이번 실행의 중간 파일만 정리한다.

다음 실제 삽입 자료는 출력 해상도를 높여도 원본 정보량이 그대로다:

- `artificial-analysis-scroll.mp4`: 1920×1080
- `artificial-analysis-index.png`: 2896×998
- `anthropic-agent-definition.png`: 1318×198
- `boris-cherny-yc.png`: 2388×1346

촬영 시 보이는 img/video/canvas의 원본 크기와 표시 크기를 보고서에 남긴다.
CSS 자르기·object-fit·숨김/등장 상태 때문에 보수적으로 잡힐 수 있는 검토 후보다.
원본 재촬영·교체의 우선순위를 정하는 자료이며 자동 불합격이 아니다. Canvas/WebGL의
고정 내부 버퍼도 제한이 될 수 있다. 강의 자료를 임의로 다시 만들지 않는다.

| 편집 때 프레임률·HDR·비정방형 픽셀 손실 | 입력 프레임률·지원 색 태그 보존, 미지원 변환 거절, SAR 정규화 |
| 결과 크기/길이가 틀려도 파일만 있으면 성공 | 편집 목표 해상도·fps·예상 길이를 검증 |
| 같은 이름 재사용과 필수 타임라인 복사 실패 | 완성 편집 덮어쓰기 방지, 필수 파일 실패 전파, 기록 임시 쓰기 후 교체 |
| 이어하기가 없는/다른 화질/다른 판본 영상을 건너뜀 | 파일 실재·화질·판본·해시 확인. 새 작업은 자동 건너뛰지 않음 |
| 성공한 정규화 MP4가 최종 영상 옆에 중복 잔류 | 검증·기록 후 이번 실행의 중간 파일만 제거. 생성 바이트 수 기록 |

정상 입력의 화질도 재검했다. 기존 비교용 PNG 6장·18초·450프레임을 수정된
제작 인코더에 넣은 결과, 이전 개선본과 디코딩된 영상의 SHA-256이 같았고
파일 크기도 **1,464,689 bytes로 동일**했다. 이 확인은 해당 입력의 결과이며
실제 브라우저 전송 안정성이나 모든 입력에 대한 무결함 보증은 아니다.

## 프레임 도착 순서 (2026-09-10 후속)

고화질(1440p) 제작이 `촬영 프레임 시각이 없거나 역전됐습니다`로 중단됐다.
덱의 `tools/capture-quality-check.mjs`를 실제 브라우저로 돌려 재현했다.
1080p는 통과하고 1440p에서 멈췄다.

원인은 시계 고장이 아니라 **전송 순서**다. 실패한 프레임의 CDP 메타데이터를
그대로 찍어 보면 직전 프레임보다 **0.70~0.82ms 이른** 시각이었다. 주변 프레임의
간격을 함께 기록하니 1ms도 안 되게 떨어져 찍힌 두 프레임이 서로 바뀌어 도착한
인접 쌍이었다. 브라우저는 스크린캐스트 PNG를 스레드 풀에서 병렬로 인코딩하고
완료 순서대로 보내므로, 프레임이 클수록 두 인코딩의 완료 순서가 뒤집히기 쉽다.
받아쓰기 쪽은 도착 순서를 촬영 순서로 믿고 있었기 때문에 이를 동기화 실패로 보고
촬영 전체를 중단했다.

경합이라 매번 나오지는 않는다. 6초짜리 1440p 촬영 6회 중 **3회**가 현재 검사에서
중단됐다. 사용자의 158초짜리 레슨은 사실상 매번 걸린다. 1080p에서 보이지 않은 것은
PNG가 작아 인코딩이 먼저 끝나기 때문이고, 4K는 프레임 자체가 드물게 와서 덜 겹친다.
둘 다 면역이 아니라 확률이 낮을 뿐이며, 실제로 4K 실행에서도 한 번 관측됐다.

수정은 `deck/tools/capture-recorder.mjs`에서 프레임을 도착 순서가 아니라 자기
시각에 맞춰 정렬해 넣는 것이다. 이미 기록한 프레임보다 오래된 프레임은 이후 어떤
출력 시각도 이길 수 없으므로 버리고, 대신 확인 응답은 반드시 보낸다. 응답이 없으면
브라우저가 다음 프레임을 보내지 않는다. 되돌릴 수 있는 지연(`LAG_MS`, 150ms)을 넘는
역전은 그대로 중단한다. 시계가 실제로 뒤로 뛰면 모든 후속 프레임이 밀려나 마지막
화면만 계속 복제되는데, 그 조용한 정지 화면을 성공으로 내보내지 않기 위해서다.
촬영 보고서에 `reordered`(뒤바뀜)와 `superseded`(밀려난 프레임) 수를 남긴다.

확인한 것:

| 검사 | 수정 전 | 수정 후 |
| --- | --- | --- |
| 6초 1440p 촬영 6회 | 3회 중단 | 6/6 성공, 3회는 뒤바뀜 1프레임을 흡수 |
| `capture-quality-check.mjs` 3해상도 | 1440p에서 중단 | 1080p·1440p·4K 모두 통과 |
| 덱 테스트 | — | 109개 통과 |
| 엔진 앱 테스트 | — | 205개 통과 |

새 단위 검사를 `tools/capture-quality.test.mjs`에 넣었다. 0.8ms 뒤바뀐 프레임이 최신
화면을 되돌리지 않는지 디코딩한 픽셀로 확인하고, 밀려난 프레임에도 확인 응답이
나가는지 센다. 정렬 삽입을 원래대로 되돌리면 앞 검사가 실제로 실패하는 것까지
확인했다.

측정하지 않은 것: 실제 ch03 레슨(158초)의 전체 제작을 다시 돌리지 않았다.
이 절은 중단 원인과 그 수정에 대한 것이며 영상 화질 자체의 재평가가 아니다.

## 4K 프레임 굶주림과 확인 응답 간격 (2026-09-10 후속)

위 수정으로 4K도 중단 없이 끝나지만 3초 촬영 75프레임 중 **36~40프레임이 복제**였다.
받은 프레임은 84장인데 그중 절반 가까이를 버리고 있었다. 원인을 프레임 시각 간격으로
좁혔다.

| 해상도 | 프레임/초 | 프레임당 PNG | 처리량 | 시각 간격 p50 / p90 | 40ms 슬롯 충족 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1080p | 92 | 1.13MB | 104MB/s | — | — |
| 1440p | 61 | 1.83MB | 111MB/s | 15.2 / 36.3ms | 99/100 |
| 4K | 29 | 3.53MB | 103MB/s | 10.5 / **91.2**ms | **48/100** |

세 해상도 모두 **약 105MB/s에서 같은 천장**에 걸린다. 병목은 해상도가 아니라 PNG
바이트 처리량이다. 4K는 프레임이 2배 커서 초당 29장이 한계다. 25fps 출력에는 그래도
모자라지 않아야 하는데, 시각 간격의 p50이 10.5ms이고 p90이 91.2ms다. 즉 **고르게
오지 않고 두세 장씩 뭉쳐 온 뒤 90ms를 쉰다**. 그래서 40ms 출력 슬롯의 절반이 새 화면
없이 남았다.

뭉치는 이유는 브라우저가 확인 응답을 받아야 다음 화면을 잡기 때문이다. 바로 응답하면
허용된 만큼(2~3장) 연달아 잡고, 그 인코딩이 끝날 때까지 멈춘다. 그래서 **확인 응답을
한 출력 프레임보다 조금 짧은 간격(40ms의 0.75배인 30ms)으로 띄웠다**. 촬영 속도를
출력에 맞춰 펴는 것이지 화면을 버리는 것이 아니다.

| 측정(3초 촬영) | 확인 응답 즉시 | 간격 30ms |
| --- | ---: | ---: |
| 4K 복제 프레임 | 36~40 / 75 | **2~10 / 75** |
| 4K 받은 프레임 | 84~85 | 93~94 |
| 1440p 복제 프레임 | 3~5 | **0** |
| 1440p 받은 프레임 | 168~171 | 102 |
| 1080p 받은 프레임 | 263~272 | 102~103 |
| 전환 시각(세 해상도) | 38~39프레임 | 38~39프레임 |

4K는 **받는 프레임이 늘고 복제가 줄었다**. 뭉쳐 오다 버려지던 몫이 실제로 쓰이는
자리로 옮겨갔기 때문이다. 1080p·1440p는 받는 프레임이 60% 줄었는데 복제는 0이다.
어차피 버려지던 프레임을 만들지 않으므로 브라우저·전송·Node 쪽 부담이 함께 줄었다.
전환 시각은 세 해상도 모두 그대로였다. 간격 비율 0.6~0.85를 훑어봤지만 차이가
기기 부하로 인한 편차 안이라 0.75로 뒀다.

`capture-quality-check.mjs` 3해상도 전체 검사를 연달아 3회 돌려 **9/9 통과**했다.
이 부하 조건은 수정 전 4K 전환 시각이 41프레임으로 벗어났던 바로 그 상황이다.

남는 한계: 105MB/s 천장 자체는 그대로다. 4K는 여전히 25fps를 겨우 채우는 쪽이고
복제 프레임이 0은 아니다. 정지 화면이 많은 강의 덱에서는 복제가 화질 손실이 아니지만,
빠른 모션을 4K로 보장한다는 뜻은 아니다. 측정은 모두 이 기기의 3~4초 합성 화면
기준이며, 실제 강의 전체 길이의 4K 제작은 아직 돌리지 않았다.

## 마지막 프레임이 잘리는 길이 버그 (2026-09-10 후속)

4K로 실제 레슨(음성 320150ms)을 만들자 촬영은 끝났는데 검증에서 멈췄다:
`촬영 규격 불일치: 3840×2160, 25fps, H.264/BT.709가 필요합니다`.

**해상도 문제가 아니었다.** 프레임 수가 하나 모자랐다.

필요한 프레임 수는 마지막 음성 구간을 덮으려고 올림한다. 320150ms의 정확값은
8003.75프레임이므로 8004프레임을 쓴다. 그래서 마지막 프레임은 음성 끝보다 10ms 더
길다. 그런데 합성 인자에 `-t`(음성 길이)와 `-shortest`가 함께 있어서, **음성이 끝나는
순간을 넘기는 마지막 프레임을 통째로 버렸다.** 결과는 8003프레임이고 검증은 8004를
요구하므로 실패한다.

즉 **음성 길이가 한 프레임(40ms)의 배수가 아닌 강의는 모두 실패한다.** 화질과 무관하다.
앞서 1440p로 성공했던 레슨은 음성이 158680ms여서 3967.00프레임으로 딱 떨어졌을
뿐이다. 3초/75프레임인 `capture-quality-check.mjs`도 딱 떨어져서 이 버그를 통과시켰다.

| 음성 | 정확값 | 필요 | 수정 전 | 수정 후 |
| ---: | ---: | ---: | ---: | ---: |
| 320150ms (실제 레슨) | 8003.75 | 8004 | 8003 ✗ | **8004** |
| 12150ms | 303.75 | 304 | 303 ✗ | **304** |
| 1510ms | 37.75 | 38 | 37 ✗ | **38** |
| 3000ms (기존 검사) | 75.00 | 75 | 75 | 75 |

수정은 두 가지다. 길이 상한을 음성이 아니라 **프레임 수에서 유도**하고(`-t` =
프레임수/fps), **`-shortest`를 뺐다**. 프레임 수를 우리가 정확히 아는 이상 `-shortest`는
불필요하고, 마지막 프레임을 자르는 쪽으로만 작용한다. 완성 파일은 음성보다 최대 한
프레임(40ms) 길어지며, 기존 길이 허용치(촬영 150ms · 앱 검수 200ms) 안이다.

합성 인자는 `captureMuxArgs()`로 꺼내 `capture-quality.mjs`에 뒀다. 인자가
`course-media.mjs` 안에 박혀 있어서 어떤 검사도 닿지 못했던 것이 이 버그가 살아남은
이유다. 이제 세 가지 소수 길이를 실제 FFmpeg로 합성해 프레임 수와 완성 길이를
확인한다. `-shortest`를 되돌리면 세 검사가 모두 실패하는 것도 확인했다.

`촬영 규격 불일치`가 어느 항목 때문인지 안 알려 줘서 원인을 다시 찾아야 했다.
이제 어긋난 항목을 짚는다: `프레임 수 8003 (8004 필요)` 같은 식이다.

실제 브라우저로도 확인했다. 소수 길이(3150ms · 정확값 78.75 · 79프레임 필요)를
1440p·4K로 촬영해 둘 다 79프레임이 나왔고 완성 길이는 3160ms였다.

측정하지 않은 것: 사용자의 320초 레슨 전체 제작은 여전히 이쪽에서 돌리지 않았다.
위 320150ms 검사는 같은 프레임 수를 작은 화면으로 합성한 것이라 4K 실시간 촬영의
성능·적체를 대신하지 않는다.

## 화질을 완전히 유지하면서 용량을 줄이는 범위

여기서 100% 보존은 육안상 비슷하다는 뜻이 아니라, 디코딩된 영상 픽셀/음성
샘플 또는 복원한 파일 전체의 해시가 같은 경우다. CRF 값이나 PSNR이 비슷하다는
이유만으로 100% 동일하다고 설명하지 않는다.

실제로 실행한 결과:

| 방법 | 시험 대상 | 크기 변화 | 동일성 |
| --- | --- | ---: | --- |
| MP4 스트림 복사 재포장 | 개선 1080p 18초 | 0% | 영상 픽셀 동일 |
| MP4 스트림 복사 재포장 | 기존 CH02 L02 전체 401.554초 | 0% | 영상 픽셀·음성 샘플 동일 |
| 완성본을 veryslow/CRF 16으로 재압축 | 개선 1080p 18초 | **+11.0%** | 픽셀 달라짐 |
| x264 veryslow/QP 0 무손실 재인코딩 | 개선 1080p 18초 | **+37.0%** | 영상 픽셀 동일 |
| ZIP Deflate 9 보관 | 기존 CH02 L02 전체 | **−1.4%** | 복원한 MP4 전체 바이트 동일 |

기존 강의 파일은 39,252,203 bytes, ZIP은 38,701,198 bytes였다.
ZIP은 재생·업로드 전에 풀어야 하므로 기본 제작 결과를 ZIP으로 바꾸지 않는다.
전체 강의의 재포장/ZIP 임시 복사본은 동일성 측정 후 제거하고 해시·측정 기록을 보존했다.
위 크기 변화는 시험 파일의 측정이며 모든 강의의 압축률을 보증하지 않는다.
veryslow 시험은 **이미 압축된 완성본의 재인코딩**이며, 첫 인코딩에서 slow와
veryslow를 비교한 결과로 확대하지 않는다. QP 0 파일은 코덱 프로필/재생 호환성도
현재 납품 규격과 다를 수 있어 제작 기본값으로 채택하지 않는다.

현재 CRF 영상은 재포장만으로 줄일 여분이 발견되지 않았다. 코덱 변경·더 높은
CRF·해상도/fps 축소는 100% 동일 조건을 충족한다고 볼 수 없어 적용하지 않았다.
실용적인 자동 절감은 중간 MP4 중복 보관 제거와 불필요한 재압축 회피다.
이전 결과, 개인 음성 정본, 완성 영상은 자동 정리 대상으로 삼지 않는다.

추가 화질 개선 후보는 실제 4K에서의 렌더/가독성 검증, 원본 자체가 낮은 해상도인
삽입 이미지·영상 교체, 필요한 경우 4K 제작 원본에서 별도 업로드본 만들기다.
4:4:4·10비트·다른 코덱·60fps는 색/모션 개선 가능성과 파일/호환성 비용을 함께
검증해야 하며 현재 3단계의 기본값을 조용히 바꾸지 않는다. 모니터 색 관리,
폰트/이미지 로딩과 CSS/WebGL의 실제 렌더 품질도 코드 검사만으로 승인하지 않는다. 반복 음성 편집의 AAC

## 외부 규격 확인 (2026-09-10)

[Playwright 영상 문서](https://playwright.dev/docs/videos)의 기본 녹화 옵션은 크기
중심이다. 프레임 획득에는 [CDP Page.startScreencast](https://chromedevtools.github.io/devtools-protocol/tot/Page/#method-startScreencast)의 PNG와 최대 크기를 사용하며,
RGB/YUV 행렬·범위는 [FFmpeg scale 문서](https://ffmpeg.org/ffmpeg-filters.html#scale)를
근거로 명시한다. 프레임 실제 크기는 문서의 기대만으로 인정하지 않고 검사한다.

[Udemy 영상 기준](https://support.udemy.com/hc/en-us/articles/229232767-Video-standards)은
최소 720p·16:9와 선명한 영상을 요구한다.
[처리 문제 안내](https://support.udemy.com/hc/en-us/articles/229233507-Instructors-Troubleshooting-video-processing-issues)는
MP4/H.264, 4GB 이하, 1080p 이하를 선호하며 4K 등 높은 해상도에는 추가 처리 시간이
걸릴 수 있다고 안내한다. 제작 원본의 4K와 모든 수강생에게 제공되는 스트리밍
해상도는 구분한다. 이 구현은 플랫폼의 4K 재생을 보증하지 않는다.
